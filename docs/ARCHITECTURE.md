## 2. Frontend ↔ backend communication (Phase 7)

- REST/JSON under `/api/v1`, with the contract in `API_SPECIFICATION.md` and the OpenAPI schema generated by FastAPI.
- Auth: the access token is sent as `Authorization: Bearer`. Refresh token storage (httpOnly cookie vs memory) is decided in Phase 3/7.
- Long-running work (uploads) returns `202 Accepted` with a job or resume ID. The frontend polls the status endpoint (SSE or WebSockets only if justified later).
- CORS is restricted to the frontend origin through settings.
- TypeScript types can be generated from the OpenAPI schema (decided in Phase 7).

## 4. Database

PostgreSQL is the single store for relational data **and** vectors (pgvector). Entities and indexes are in `DATABASE_SCHEMA.md`. Migrations go through Alembic only.

## 5. AI layer

- `EmbeddingProvider` (Protocol), implemented by `SentenceTransformerEmbeddings`. It runs locally in the worker and is loaded once per process.
- `LLMProvider` (Protocol), implemented by `GeminiLLM`. A `FakeLLM` is used for tests.
- Prompts are versioned in `app/ai/prompts/`. Retrieval code is written directly with SQLAlchemy + pgvector (no framework, TD-008).

## 6. RAG ingestion flow (Phases 4–5)

```
POST /resumes (or /resumes/bulk)
 → validate (MIME, extension, size, count) → SHA-256 checksum (dedupe)
 → save file → INSERT resumes(status=uploaded) → enqueue process_resume(resume_id) → 202
Celery: process_resume
 → status=processing
 → extract text (PyMuPDF / python-docx, keep pages)
 → clean (normalise Unicode, whitespace, headers/footers)
 → parse sections + fields (contact, skills, experience, education) → upsert candidate + skills
 → chunk (section-aware, ~200–400 tokens, overlap)            [Phase 5]
 → embed in batches → INSERT resume_chunks(embedding, metadata) [Phase 5]
 → status=processed  | on error: status=failed, error_message (retry with back-off for transient errors)
```

## 7. RAG retrieval flow (Phases 5–6)

```
POST /rag/ask {question, candidate_ids?, filters?}
 → embed question (same model as documents)
 → retrieve: pgvector cosine top-k + metadata WHERE filters
     [Phase 6: + full-text search → RRF fusion → optional cross-encoder rerank]
 → similarity threshold check → if too low: "not found in provided resumes"
 → build context: labelled chunks [chunk_id | candidate | section], token budget
 → LLMProvider.generate(system prompt with grounding + citation + injection rules, context, question)
 → parse and validate citations against the supplied chunk IDs
 → log query metadata (no resume text) → response {answer, citations[], retrieved_chunks[]}
```

The matching flow (Phase 6) reuses retrieval plus structured skill and experience signals, and stores component scores and an explanation per (job, candidate).

## 8. Background processing (Phase 4)

- Redis is the Celery broker (and result backend if needed).
- Tasks are idempotent, keyed by `resume_id`, with retries plus back-off for transient failures only.
- Workers own CPU-heavy work (parsing, embedding). The API never blocks on it.
- Bulk uploads are tracked through `upload_batches`, with per-file status.

## 9. Deployment architecture (Phase 8, proposed)

```
GitHub → GitHub Actions (lint, test, build images) → registry
Host (AWS EC2/Lightsail or a VPS, TD-019):
  docker compose: nginx/caddy (TLS) → frontend (Next.js) + api (uvicorn/gunicorn)
                  worker (celery) · postgres+pgvector (or managed RDS) · redis
Secrets: environment variables / host secret store. Never in images or the repository.
```

## 10. Cross-cutting concerns

- **Security:** JWT + RBAC, upload validation, CORS, rate limiting (Phase 8), and no PII in logs.
- **Privacy:** synthetic data only in development. Only synthetic content goes to the LLM.
- **Explainability:** every score has components and evidence; every answer has citations.
- **Observability:** standard logging (structured logging in Phase 8) and request IDs.
